## Connect the private Google Sheet

This checkout was connected on 2 November 2026. A live metadata write/read-back and the dashboard's Refresh Sheet action both succeeded. Existing financial input amounts were preserved. The original JSON key was moved from the repository root into the ignored, owner-only `.secrets/household-service-account.json`; the runtime uses the encrypted copy in `.household/google.enc`. Those private directories are not part of Git or the public build, so another checkout still needs its own local setup.

The local read/write integration is implemented. It is **not activated or live-verified until you supply a service-account key and complete setup**. Keep the workbook's General access set to Restricted. This does not publish the website.

1. In [Google Cloud Console](https://console.cloud.google.com/), create or select a personal project and enable **Google Sheets API** under APIs & Services → Library.
2. Open IAM & Admin → Service Accounts. Create a dedicated account named `household-dashboard`. Skip the optional project roles and user-access grants; it needs no Google Cloud project Editor/Owner role or domain-wide delegation. See [Google's service-account instructions](https://docs.cloud.google.com/iam/docs/service-accounts-create).
3. Open the service account → Keys → Add key → Create new key → JSON. Save the downloaded file outside this repository, such as Downloads. Keep the private key out of chat, source control and shared folders. See [Google's key instructions](https://docs.cloud.google.com/iam/docs/keys-create-delete).
4. In your existing finance workbook, use Share to give that service account's email **Editor** access. Share only this workbook, not a folder or your entire Drive.
5. From the website directory, run `npm run connect:household -- "/absolute/path/to/the-downloaded-key.json"`. Alternatively, give Codex the local file path to finish this authorized setup. No key contents need to be pasted.

Setup checks Google access and the existing headers, compares the local plan with the source, and stops if financial inputs differ. It preserves the original plan amounts, evidence columns and unrelated formulas. The exceptional wife-share formula is updated to respect the newly explicit payer when an item is not shared. It adds `Recurring Plan!W5:W65` (Stream ID), `Exceptional Costs!S5:S65` (Payer / recipient), and the `Dashboard Properties`, `Dashboard Assets` and `Dashboard Meters` register tabs. The registers start with local property/asset/reading records. Setup uses an atomic Google batch for these additions, then reads back and validates the workbook before confirming the connection. An existing partial or different schema requires review, not automatic replacement.

After setup, reload the dashboard. **Saves go directly to Google Sheets and are read back before confirmation.** Click **Refresh Sheet** to import changes made in Google Sheets; the dashboard shows the last successful check time. It does not poll in the background. A failed refresh retains the previous snapshot. Connected mode never silently saves offline. A save with an uncertain outcome blocks further edits until Refresh checks what Google accepted; writes are never automatically replayed.

Recurring and exceptional inputs stay in rows 6–65, matching the workbook's current formulas. Additions and dated recurring versions consume free rows. Setup does not extend those formulas silently; a full input area requires an explicit workbook extension. Each additional register supports rows 2–1001. Keep IDs, headers and Stream IDs intact; end/exclude items rather than deleting historical rows. For new properties, links use the stable property ID in the dropdown. Exception payer is explicit, separate from sharing.

The app detects changes by comparing the last-read input/formula/validation fingerprint immediately before saving and patches only changed fields. **Google Sheets does not provide a transaction spanning a read and a later write**: avoid editing the same field in Sheets during a dashboard save. Separate dashboard processes/computers are not coordinated. A single local instance serializes its writes. For stronger concurrency guarantees, a transactional database should become the authoritative backend. See [Google's batch update behavior](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate).

The service account uses the Sheets scope with access limited in practice by its workbook sharing. Credentials are encrypted server-side in `.household/google.enc` using the same local key as the private financial store. They are not returned to the browser. Remove workbook sharing or disable the service-account key in Google to revoke access. After connection, secure the original downloaded JSON independently; the app does not delete it. To rotate, download a replacement, rerun connection setup, verify access, then retire the old key in Google.

## Private storage and access

`.household/` is ignored by Git and excluded from the public build. It contains the scrypt PIN verifier, encryption key, encrypted state, persistent attempt counters, and encrypted revision backups. Files use owner-only permissions. The key is stored locally alongside the verifier: encryption protects accidental data-file disclosure; it does not protect against compromise of the computer or loss of the entire directory. Keep the directory out of source archives and shared folders.

Use `npm run setup:household` in your own terminal to choose a new PIN without echoing it. Rotation preserves data and invalidates sessions. Losing the local key prevents recovery of the encrypted data and backups. Keep an independent secure backup. No recovery link, universal PIN, or authentication bypass is provided.

Every financial response, UI asset, and mutation requires a server-side session. Sessions have a 15-minute idle limit and eight-hour maximum, HttpOnly/SameSite cookies, same-origin checks and mutation CSRF tokens. The preview binds only to loopback and rejects unexpected Host headers. Attempt limits survive server restarts. No financial data, session token or PIN is stored in localStorage, a service worker, analytics or a public asset.

`api/household.js` deliberately returns unavailable on hosted deployments. The functional handler is local-only and also refuses Vercel execution. No publishing, live routing, live settings or public financial access has been enabled. Production work needs a separate review of durable private storage, TLS, session and rate-limit storage, and backup/recovery before the owner manually publishes. The service-account integration runs only on the local server.

## Financial model

My finances exposes the selected month's personal income lines, allocated recurring costs, ETF transfers, exceptional bills/refunds and living allowances, with subtotals and a full income-minus-outgoings calculation. Wife-paid personal costs and her salary are omitted. Joint receipts remain explicitly labelled and are included in full under the user's chosen cash scope. Refunds offset personal exceptional spending once. Unlike the no-invoice forecast, this page includes known exceptional items for the selected month. Both pages share the same personal cash calculation.

The recurring page has Both shares, Only my share and Only my wife's share views. Monthly totals remain fixed while searching/filtering and include costs plus ETFs due in the selected month, excluding exceptional invoices. Allocation uses integer cents; any indivisible cent is assigned once, so the two contributions reconcile to the full payment.

The dedicated Forecast page models six complete monthly cash-flow cycles using the versions active in the selected planning month. It freezes those amounts (ignoring later price versions, while retaining a known schedule end when no later version exists), keeps quarterly/annual payment dates and known final payments, excludes exceptional invoices and later price versions, and deducts €500 groceries plus €300 miscellaneous from the user's personal surplus each cycle. It includes income received by the user and full joint-account receipts, as confirmed by the user; the wife's salary is excluded. It assumes the wife's planned cost contributions arrive on time. The latest dated Cash asset supplies the opening balance, and its name/date are shown. Without one, the page shows additional cash rather than inventing a bank balance. This scenario does not reconcile past payments already in the opening cash or model precise bank posting dates. It is not a forecast of an exact calendar-day balance. Living allowances are scenario assumptions and do not create recurring bills in Sheets.

Amounts are whole EUR cents. The monthly result is scheduled household income minus full recurring cash commitments, exceptional costs and ETF funding. It excludes daily spending. It is a plan, not a live bank balance or guaranteed savings. Internal wife reimbursements are not additional household income. Her displayed allocation is a planned contribution, not confirmation of a received transfer.

Monthly, quarterly and annual schedules use a first-payment month and optional last active month. A later change creates a new version and closes the prior version; overlapping versions are rejected. Editing the initial effective month corrects that draft version and retains its prior state in the encrypted audit history. Exclude or end items rather than deleting financial history. Unknown values stay null. Property ownership does not automatically determine expense-sharing. Property values are dated estimates, and equity appears only when both value and debt are recorded. Add assets and properties through their forms; map recurring items to a property explicitly.

Quarterly/annual provisions use differences between rounded cumulative amounts, so a full period reconciles to the exact billed cents. These provisions are an alternative planning view and are not deducted a second time from cash left.
